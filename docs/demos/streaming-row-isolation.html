01 / 变长的不是一条数据，是一门父级几何

为什么兄弟行会跟着倒霉

文本增量 → 直流行 subtree 高度变化 ①
　　　　　 → 父级 VStack 高度变化 ②
　　　　　 → 所有子行 placeSubviews / sizeThatFits ③
　　　　　 → 未变的 99 条历史 × 每一次增量

③里没有任何“内容变了”，但它们的几何依赖了②，于是每次增量都被动重算。实测里这正是热点的形状：增量到达时，热点是栈布局机器（placeSubviews、sizeThatFits、AG 遍历），而不是 Markdown 解析或文字排版。

实测参考（单次·非性能跑分）：同输入强制布局下，复杂历史 100 行 +3.1s；把历史换成短文本后 +0.20s；复杂直播体自身 +1.3s。隔离的最大的那块，正是①→③的链路。
02 / 隔离的不是内容，是布局所有权

直播行搬家后少了什么

外层 VStack
├─ 历史容器（172 缓冲 + 视口 + 99 条）✋ 不再知道
└─ 隔离容器（只装直播行）
　　└─ 直流行 subtree ①②③ 都留在这里

隔离容器内部仍然要随增量重排——这必须发生，不是免费。省掉的是外泄：外层高度对齐只发生一次/次，兄弟行的几何不再被牵连。窗口滚动、锚点恢复、工具分组等机制理论上复用现状，但需要把这些 CSR 路径全部重测。

同样保留现状的还有 Store 侧：排队、按序处理、失败快照修复都不动。这一步只动布局，不碰事件语义。
