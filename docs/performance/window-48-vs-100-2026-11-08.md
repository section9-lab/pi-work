# Window 48 vs 100 — 2026-11-08

Status: controlled single-run comparison of the current transcript implementation
(token batching, tail-only Markdown parsing, offscreen render gate, measured
placeholder virtualization). This is a diagnosis record, not an acceptance run.

## Method

- Staged `after` sources from commit `075028f`; only
  `TranscriptWindow.batchSize` was overridden to 48 in the staged copy. Every
  other file, including the test harness, was identical.
- Release build with `-enable-testing`, 840 × 640 pt surface, in-process fake
  host, 1,000 mixed-complex history sources, ~9.3 KB complex live body.
- Same machine, sequential runs: 100 then 48. Load average 3.5–4.0 and ~2.97 GB
  swap used in both runs. One observation per scenario; no repeats.
- `scripts/MarkdownIsolationPerformance.swift` now waits for
  `TranscriptWindowNavigation.maximumCount` rows instead of a hardcoded 100, so
  both variants use the same harness.
- Artifacts: `build/TranscriptAcceptance/ab-window100-2026-11-08/` and
  `build/TranscriptAcceptance/ab-window48-2026-11-08/`.

## Interpretation

- Window 48 cuts the per-publish p95 stall by roughly 10× when mounted and 20×
  under forced layout, and cuts process CPU by 37–40% for 1,000-source history.
  Publication cadence improves from 8–9 rounds to 25–27; with 100 rows the main
  actor misses most coalesced windows.
- Publish lag stays around 1.05 s. The maximum gap is 1.04–1.10 s in every
  scenario, including three history rows. That tail is a single completion
  stall, not per-publish stack work, and window size does not move it.
- The remaining tail is the completed live reply's final full render/first
  layout. Prior container and separate-`NSHostingView` isolation experiments
  were negative for the per-publish stack sweep, and this comparison does not
  support isolating the live row as the first fix for the 1.05 s tail.

## Recommendation

1. Promote `TranscriptWindow.batchSize = 48` in production and recalibrate the
   history/prefetch timing tests. The p95/CPU tradeoff is decisive; window 100 is
   no longer justified after virtualization. **Implemented:** production now
   uses 48, with adaptive window expectations in the history and prefetch tests.
2. Then profile the ~1.05 s completion stall separately. It is the new dominant
   lag and appears with only three history rows; likely the final full parse and
   first layout of the completed complex Markdown body.

## Limits

- Single run per configuration on a loaded machine with swap in use; the 48 build
  was a staged override, not a committed production change.
- No pixel/FPS or GPU measurement; render checks are the existing weak mounted
  presentation check. The fake host does not cover IPC, disk, or network.
