# 复杂 Markdown：现有 100 条 vs 固定 100 条＋流式隔离

日期：2026-11-04。**这是探索性 A/B，不是“优化后全线更快”的结论。**

主要发现：

1. 同等缓存历史覆盖范围的总耗时下降约 **14%**，阶段累计峰值 RSS 下降约 **49%**。
2. 阅读历史时后台生成新回复，测试进程 CPU 时间下降约 **56%**。
3. 首次展示 100 条复杂消息几乎没有改善；极密集内容仍约 **48 秒**。
4. 同等 Host 历史覆盖范围反而慢约 **11%**，因为固定窗口需要更多导航动作。
5. **基线存在复杂流式正文末尾未刷新问题。实时跟随项不能公平计算提速倍数。** 候选的完整正文校验通过。

所有候选改动只存在于 `build/MarkdownIsolationBenchmark/` 的独立源代码副本；没有把这套原型改入生产 `PiWork/` 源文件。

## 1. 文档复杂度和负载

完整 fixture：[performance-complex.md](../../PiWorkTests/Fixtures/markdown/performance-complex.md)。替换占位符前为 **4,609 UTF-8 字节、121 行**，包含：

- H1–H6 六级标题。
- Swift、TypeScript、Python、SQL、JSON、diff、Bash 七类 fenced code，以及长代码行。
- 五列表格与对齐、嵌套有序/无序列表、任务清单、多层引用。
- 粗体、斜体、删除线、行内代码、链接、分隔线、转义字符。
- 中文、English、emoji 混排；不加载远程图片或资源。

语言标签不等于语法高亮：实际执行的是应用现有 MarkdownUI 主题和代码块展示路径，没有额外引入高亮器。

### 两档负载分别记录，不能混为一谈

| 负载 | 完整会话 | 初始 100 条窗口 |
| --- | --- | --- |
| 密集压力档 | 1,000 条源消息 | 80 份完整复杂文档＋20 条短用户消息 |
| 混合会话档 | 1,000 条源消息 | 10 份完整复杂文档＋70 条较短 Markdown 回复＋20 条短用户消息 |

较短回复仍有标题、代码块、表格、嵌套列表和引用，不是空白占位。密集档在较早的独立批次测冷打开，作为极端负载观察；混合档测完整流程。

**流式正文不使用简化版**：每个回复拼接两份完整复杂文档，实际为 9,299 / 9,335 字节。按字符切为 148 / 149 个增量，名义间隔 20 ms，刻意跨越标题、表格和未闭合代码围栏。记录实际输入时长，不假定后台调度一定精确达到 50 Hz。

## 2. 比较的实际实现

两组初始窗口都为 100 条，使用真实 `SessionStore → ChatView → ChatMessageRow → AssistantMarkdownView → MarkdownUI`。

- **基线**：现有父层订阅、窗口投影和 `100 → 200 → 300` 历史窗口策略。未变化行仍有原有 equality 复用，不把基线故意改成每次重解析全部 Markdown。
- **候选**：固定 100 条，向前移动 60 条、保留 40 条重叠；正文增量由当前回复模型接收；结构事件仍通知父层；窗口投影按会话、结构更新代数、导航、展示上限和执行状态缓存，避免几何更新导致重复扫描整段会话。
- Store 原有 80 ms 发布窗口、Markdown 原有 200 ms 合并周期保持不变。没有虚构忙循环或增加无用运算来放大差异。
- 对照与候选在同一档 A/B 中执行同一个实验 Release 二进制，以一次读取的环境开关切换策略。

历史计时既测单次动作，也测**相同源消息覆盖范围**。这很重要：候选每步前移 60，不应把它与基线每步前移 100 简单当成相同工作量。

## 3. 本轮可比较结果

**每档每配置目前只有 1 次观测。** 机器非独占，存在其他应用负载。下面是本轮观测值，不是稳定的跨机器速度承诺；百分比只描述这一次 A/B。

### 混合会话档

| 场景 | 基线 | 候选 | 本轮差异 |
| --- | ---: | ---: | ---: |
| 冷打开，完整初始 100 条 | 9.412 s | 9.412 s | 基本不变 |
| 已打开会话重新挂载 | 10.015 s | 9.030 s | 耗时约 -10% |
| 缓存历史第一次前移 | 8.024 s，200 行 | 5.590 s，100 行 | 单次约 -30%，前移量不同 |
| 缓存历史第二次前移 | 10.938 s，300 行 | 5.371 s，100 行 | 单次约 -51%，前移量不同 |
| 缓存历史第三次前移 | 13.986 s，300 行 | 5.398 s，100 行 | 单次约 -61%，前移量不同 |
| **相同缓存历史覆盖：向前 300 条** | **33.277 s，3 次动作** | **28.540 s，5 次动作** | **总耗时 -14.2%** |
| **上述阶段测试进程累计峰值 RSS** | **1,334 MiB** | **674.8 MiB** | **约 -49.4%** |
| **相同 Host 历史覆盖：向前 200 条** | **18.256 s，2 次动作** | **20.255 s，4 次动作** | **总耗时反而 +11.0%** |
| 返回最新、重新挂载 | 11.057 s | 10.456 s | 约 -5% |
| 响应进入 failed 状态 | 3.966 s | 3.981 s | 基本不变 |

RSS 是从进程启动到该点的**累计峰值**，不是瞬时内存、该动作新增分配量，也不是对整个应用内存的承诺。

相同缓存历史覆盖下，两组都新建了 240 个 Markdown presentation；候选并不是靠漏画那些新进入窗口的消息取巧。窗口投影次数为 **34 → 6**，累计扫描源消息为 **34,000 → 6,000**。但这些计数下降不等于耗时也按相同比例下降：真实的 Markdown 视图创建和布局仍然昂贵。

### 阅读历史期间开始生成新回复

本场景先固定历史阅读位置，再开始新的回复；新回复在**两侧历史窗口之外**。它测的是历史阅读区对后台新正文的响应，不是两侧都显示当前回复的解析性能。

| 指标 | 基线 | 候选 |
| --- | ---: | ---: |
| 测试进程 CPU 时间 | 6,451 ms | 2,809 ms（-56.5%） |
| 场景墙钟时间 | 6,912 ms | 4,596 ms |
| 主线程采样间隔 P95 | 407 ms | 10.7 ms |
| 窗口投影次数 | 8 | 2 |
| 直接跳过的父层正文通知 | 0 | 33 |
| 新回复的 Markdown 发布次数 | 0 | 0（窗口外，不应绘制） |

两组均核对最终 Store 正文与全部输入完全一致、事件序号连续、没有额外快照修复，历史阅读锚点偏差不超过 2 pt。随后重新挂载最新窗口，校验窗口外积累的完整正文进入渲染模型。

P95 是带显式布局的主线程调度采样间隔，**不是 GPU 帧时间、FPS 或真实用户输入延迟**。CPU/墙钟也包括阶段收尾和状态切换开销，不能把这部分收益完全归因于订阅隔离：候选还同时减少了历史挂载行数。

### 密集压力档：100 条中有 80 份完整复杂文档

| 指标 | 基线 | 候选 |
| --- | ---: | ---: |
| 完整初始窗口 | 47.635 s | 47.799 s |
| CPU 时间 | 47.374 s | 47.512 s |
| 应用现有首帧埋点 | 922 ms | 861 ms |
| 窗口投影次数 | 35 | 9 |

两组完整初始化的 Markdown presentation 都是 80 个。**减少投影并没有解决一次挂载大量复杂文档的布局成本。** 不能因为不到一秒已有首帧，就认为整个窗口不到一秒完成。

该档各 1 次，较小差异不应解释为稳定回退或提升；它与混合档来自不同采样批次，不横向比较两档的细微百分比。

## 4. 实时跟随：正确性失败，不能算提速

这个结果比一个漂亮的 CPU 百分比更重要：

1. 小型可见性回归使用 3 条短历史消息，加上约 9.2 KB 的复杂流式回复。
2. 基线 Store 已处理全部事件，`lastSequence = 151`，预期也是 151。
3. 但实际仍存活的 `AssistantMarkdownPresentation` 最后收到并渲染的文本只有约 7.5 KB；最终正文应为 9,224 字节。
4. 为排除实验行包装的影响，另外换回**原始 ChatView 路径**复测，同样可复现：渲染模型 `requested_bytes = rendered_bytes = 7,484`，Store 已到序号 151。
5. 候选相同校验达到 `requested_bytes = rendered_bytes = 9,224`，检查通过。
6. 正式混合档的实时跟随也复现：基线渲染模型停在 8,181 字节，最终正文应为 9,299 字节；该记录标记 `final_render_valid = 0`。候选 `final_render_valid = 1`。

这是**模型到界面的最终版本未传递/刷新**现象，不能据此断言是 Markdown 解析器丢字符；具体根因尚未定位。本轮没有把根因修复直接写入生产代码。

这些检查不是读取一个可能被覆盖的全局“最后渲染计数”，而是通过弱引用检查仍存活的实际 presentation 对象及其请求/渲染正文。两组实时跟随测试均由驱动保持尾部可见，以减少滚动位置对观测的干扰；这不等于测过全部原生自动跟随行为，也不是像素级截图验收。

**因此，不提供基线与候选实时跟随的 CPU/耗时提速倍数。** 少绘制末尾内容的基线不能参与公平比较。原始数据保留，汇总脚本将这一整项标记为 INVALID，而不是把正确性失败包装成性能优势。

## 5. 验证状态

- 两个策略分支的通用回归各 **96 项通过**：Markdown 合并/刷新、时间线、Store reducer，以及新增的结构事件通知边界和窗口导航边界。
- 独立复杂流式渲染检查：**基线失败，候选通过**，失败日志不隐藏。
- 场景采集脚本完成；共 **24 条场景记录**，其中实时跟随的基线记录无效，整组不计算性能比。这不等于“24 项正确性全部通过”。
- 实际分页、缓存覆盖、锚点、Store 正文、事件顺序、历史耗尽与重新挂载均有断言。
- 历史合成滚轮输入放在聊天空白边距，且确认真正触发用户滚动，避免误落入代码块的横向滚动区域而形成假超时。

## 6. 结论与下一步

**这套方案值得推进，但不能直接宣称“展示 100 条的问题已经解决”。**

- 固定窗口对历史阶段的内存和单次响应有明显价值；同覆盖总耗时收益更温和。
- 每步移动 60、取回 100 的策略存在额外缓存导航成本；Host 历史总耗时这次更慢，需要继续调整预取/推进策略。
- 隔离正文更新能减少历史阅读区的工作；仍需覆盖同一回复生成中切到历史、多代消息交错、工具/审批/图片及取消竞态等完整 UI 场景。
- 先把“末尾完整正文必须进入渲染对象”固化为回归，再定位基线刷新问题。修复正确性后，才能对实时跟随作公平的性能对比。
- 如果目标是 100 条都很长、很复杂时依然快速打开，还要继续做实际视图复用/虚拟化、减少完整 Markdown 块重建等优化，单靠固定窗口和订阅隔离不够。

## 7. 环境、复现与证据

Apple M5 / 16 GB / macOS 26.6 / Swift 6.4.2；Release `-O`、开启测试可见性；原生窗口 840 × 640 pt。Host 是确定性进程内 fixture，不包含真实磁盘、网络或 provider 时延。不读取当前用户的会话文件。

本轮混合档实际执行的是 **A/B 各一次**，不是 A/B/B/A；密集冷打开也各一次。机器非独占，结果只作探索性判断。此前 40/100 的 fixture 较简单，不能拿那份报告的绝对耗时直接与本次相比。
