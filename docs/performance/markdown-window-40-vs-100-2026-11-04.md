# Markdown 消息窗口：40 vs 100 性能实测

日期：2026-11-04。结论：**100 条窗口的主要成本在完整布局、历史扩展和会话切换，而不是首帧；不能仅凭功能测试通过认为性能无回退。**

本次没有改生产窗口大小或渲染实现。所有 A/B 修改都在 `build/MarkdownWindowBenchmark/` 的独立源代码副本中进行，保留工作区已有修改。

## 方法

- Apple M5，16 GB，macOS 26.6；Swift 6.4.2，Release `-O`，开启测试可见性。
- 实际 `SessionStore → ChatView → ChatMessageRow → AssistantMarkdownView → MarkdownUI`，不是只测解析器，也不是简化版聊天视图。
- 原生窗口 840 × 640 pt。等价的 1,000 条消息：20% 用户消息、80% Markdown 回复，含标题、代码块、表格、嵌套列表、引用、链接和中文；每次迭代使用不同 salt，避免把已有解析缓存当冷数据。
- 顺序 **40 → 100 → 100 → 40**；每轮两次，每个配置/场景共 **4 个样本**，共 **112 个场景样本**。下表为中位数，没有删除异常值。
- 仅切换 `TranscriptWindow.batchSize`，其他策略不变：历史窗口最多为批大小的三倍（120/300）；首批 4 条，随后每批增加 12 条；生产 Markdown 流式合并周期 200 ms。
- 确认真实行几何数量和文档高度连续三次稳定后才结束布局计时，不是等待固定时间后猜测完成。观察周期 10 ms，稳定检查带来共同的约 30 ms 下限。
- CPU 为测试进程用户态＋内核态 CPU 时间；墙钟时间含调度、布局及稳定等待。不是 GPU 帧率测试。

## 打开、历史和会话状态

单位：秒，均为一次操作完成后的墙钟中位数。

| 场景 | 40 | 100 | 100/40 |
| --- | ---: | ---: | ---: |
| 长会话冷内容：完整初始窗口 | 1.546 | 4.297 | **2.78×** |
| 已打开会话重新挂载视图 | 1.581 | 4.258 | **2.69×** |
| 缓存历史：第一次扩展，80/200 行 | 1.077 | 2.358 | 2.19× |
| 缓存历史：第二次扩展，120/300 行 | 1.372 | 3.307 | 2.41× |
| 缓存历史：在上限内向前滑动，120/300 行 | 1.739 | 5.259 | **3.02×** |
| Host 历史页：第一次加载＋布局 | 1.181 | 2.874 | 2.43× |
| Host 历史页：第二次加载＋布局、到达历史起点 | 1.927 | 3.210 | 1.67× |
| 同一 ChatView 切换到另一已打开的长会话 | 2.679 | 6.415 | 2.39× |
| 同一 ChatView 切回原长会话 | 2.518 | 4.781 | 1.90× |
| 当前响应进入 failed，保留内容并展示错误状态 | 0.395 | 0.667 | 1.69× |
| 空会话（含固定 100 ms 等待） | 0.133 | 0.134 | 1.01× |
| 10 条短会话 | 0.594 | 0.432 | 0.73×，不应解读为稳定提升 |

冷内容完整窗口的 CPU 时间为 **1.509 → 4.071 秒，2.70×**；缓存历史滑动的 CPU 时间为 **1.716 → 5.115 秒，2.98×**。因此差异不只是固定等待时间造成的。

应用现有首帧埋点为 **343 → 327 ms**，基本相当。首帧不是整个窗口准备完毕：两种配置都从少量消息开始呈现，100 后续需要补齐更多行。

**历史每次加载的工作量不同**：100 每次提供的行数是 40 的 2.5 倍；这些数字比较的是窗口策略和单次操作延迟，不是相同 100 条历史数据的总遍历耗时。

## 实时增量输出

独立于主线程的生产者以 50 次/秒发送 100 个增量，真实经过事件流、reducer、视图更新和生产 Markdown 合并逻辑。最终切回 idle，包含末尾刷新。

| 场景/指标 | 40 | 100 | 差异 |
| --- | ---: | ---: | ---: |
| 跟随最新输出：CPU 时间 | 1,361 ms | 1,699 ms | **+25%** |
| 跟随最新输出：主线程采样间隔 P95 | 47.1 ms | 60.5 ms | +28% |
| 阅读历史，后台继续输出：CPU 时间 | 1,102 ms | 1,708 ms | **+55%** |
| 阅读历史，后台继续输出：主线程采样间隔 P95 | 44.0 ms | 80.1 ms | +82% |

两种配置的流式场景墙钟时间都约 2.5 秒，因为输入时长被固定了，不能用这个相近数字判断性能相同。表中的 P95 是各样本 P95 的中位数；采样间隔包含显式布局，**不是显示器帧时间或真实用户输入延迟**。

## 状态和正确性验证

四轮性能测试均通过，计时过程中同时检查：

- 冷打开和已打开会话缓存复用；缓存重开不重复执行 open RPC。
- 历史窗口扩展、达到上限后的滑动、两次 Host 分页及历史耗尽。
- 缓存历史加载后原有行的锚点偏差不超过 2 pt。
- 正在跟随输出和暂停跟随阅读历史两种状态；历史阅读锚点不被新消息拉走。
- 每轮 100 个增量均进入最终内容，核对消息 ID、消息数量及连续事件序号；没有用触发快照修复的丢弃事件冒充后台输出。
- 流式 running → idle、切换已打开会话、返回原会话、running → failed，以及空/短会话。
- 关闭测试窗口时显式卸载 SwiftUI 树，避免已关闭的视图继续订阅 Store、污染下一场景。

另外，在 **100 配置**运行 Markdown、时间线、压缩展示、窗口导航、滚动观察和相关真实聊天历史/流式 Store 测试，**101 项全部通过**；在 **40 配置**补跑 Markdown 的合并、完成立即刷新、取消及恢复测试，**3 项全部通过**。

## 波动与边界

- 这是使用可复现合成内容的原生聊天视图基准，**不是读取当前用户会话文件的生产现场测量**。
- 本机并非独占环境，存在应用、WindowServer 和其他后台任务负载；每个场景只有 4 个样本，不能把倍数当成精确的跨机器保证。
- 墙钟波动较大：冷窗口 40 为 1.08–2.44 s，100 为 3.02–6.68 s；缓存历史滑动 40 为 1.47–7.42 s，100 为 4.45–7.08 s。保留了这些慢样本，CPU 和墙钟应一起看。
- Host 使用确定性的进程内 fake；“Host 历史页”测的是获取返回后的真实合并与展示链路，不包含真实磁盘、网络或模型服务延迟。
- “冷”指新 Markdown 内容，不是冷进程/冷文件系统；重新挂载已打开会话与在同一视图切换会话分开测量，Store 缓存也不等于所有 Markdown 都命中解析缓存。
- 没有测内存峰值、GPU FPS、真实 provider 吞吐、图片、大型工具输出、审批弹窗或所有压缩/取消竞态的性能。

## 建议

若优先保障响应性，当前实现更适合保留 **40 条渲染窗口、120 条历史布局上限**。若希望每次加载 100 条，可考虑把“Host 获取页大小”和“实际渲染窗口”解耦，而不是同时把 `VStack` 的布局上限提高到 300。首帧快并不代表完整窗口开销小；后续优化应优先看完整窗口布局及历史阅读期间的主线程工作。

## 复现与产物

```bash
bash scripts/benchmark-markdown-window.sh
```

需 macOS、Xcode 和可用的 WindowServer 会话；不修改生产源文件。默认输出到 `build/MarkdownWindowBenchmark/`：

- `environment.txt`：环境、Git HEAD、关键暂存源文件 SHA-256。
- `run-40a.log` / `run-100a.log` / `run-100b.log` / `run-40b.log`：四轮通过的原始输出。
- `results.json`：112 条结构化样本。
- `summary.md`：全部指标的中位数、倍数及墙钟范围。
- 本次额外的 `regression-100.log`、`regression-40-markdown.log`：回归验证日志。

实现：`scripts/MarkdownWindowPerformance.swift` 只在独立测试副本中追加至现有 Store 测试，复用其私有 Host fixture；`scripts/summarize-markdown-benchmark.py` 汇总结构化输出。普通应用构建不包含这个性能驱动。
